### 属性文法类比表（可直接做成表格）

| 属性文法 | 行为树 Tick | 说明 |
|---|---|---|
| 继承属性 | 环境 σ | 自上而下传递，子节点只读 |
| 综合属性 | 子节点状态 st | 自下而上返回，父节点据此定值 |
| 属性求值 | 一次 tick | 单遍、自底向上；RUNNING 相当于"求值挂起" |
| 增量/惰性求值 | Sequence/Selector 的续跑指针 | 下次从断点继续，不重复求值已成功的子树 |
| 不动点迭代 | 反复 tick 直到根节点终止 | 整棵树执行 = tick 的最小不动点 |

## 2. 讲清楚"为什么需要形式语义"的三个具体差异

1. **并行节点的成功条件**：`Parallel(k)` 里 k 的含义、失败判定是"任一失败"还是"剩余不可能达标"，
   不同引擎不一样；本仓库采用后者（`fail > n - k` 立即失败），并在 `S-PAR-F` 规则里写明。
2. **中断/抢占**：带记忆的 Selector 在低优先级分支 RUNNING 时**不会**回看高优先级条件。
   `examples/guard.json` 的 P1 反例（调小 `sustain` 就能复现）正是这一点的直接后果 ——
   这不是 bug，而是语义选择；引擎如果不说明，行为就无法预测。
3. **记忆的生命周期**：节点返回 S/F 后记忆是否清零，决定了"同一棵树两次 tick 是否等价"。
   本仓库把它上升为不变量（README §2.3），并用 `tests/test_tree.py::test_memory_reset_after_terminal` 固定住。

## 3. 算力规划怎么写（模板）

先给公式，再填实测数字：

```
可达状态数   |S|  ≈  Π_{i=1..w} d_i            （w 个并行分支，动作时长 d_i）
转移边数     |δ|  =  |S| × 2^m                  （m 个原子命题）
BMC 编码规模 ≈  |δ| × k + |S| × k              （k 为 horizon）
显式存储     ≈  |S| × (每条记忆 8 字节 × 节点深度) 
```

举例（把 `build/bench.md` 的实测值代进去）：

* w=9、d∈{2,3,4} 时状态数已到 1.6×10^5 量级，转移边 6.6×10^5；
* 若把 atomic 命题增加到 6 个（2^6=64 种环境），转移边数立刻放大 16 倍；
* 继续加宽到 w=12，状态数进入 10^7，显式 BFS 的单机内存与时间都不可接受。

由此提出云端算力的三条需求（报告里建议按这个结构写）：

1. **纵向**：符号化 + 更好的编码（用 `z3` 的 `Solver` 分块、或换 NuSMV 的 BDD）——先榨干单机；
2. **横向**：状态空间按"顶层子树组合"切分，多机并行探索再合并（MapReduce 式 BFS）；
3. **预算**：给出每个规模档位的预估机时（本仓库 `--state-limit` 就是预算控制点，超限抛 `StateExplosion`）。

## 4. AI 协作记录（附录素材）

可以直接引用的提示词（建议在报告里贴 2~3 条，并说明"生成后如何核查"）：

* "把行为树的 Sequence 节点用结构操作语义写成推理规则，前提/结论用数学符号，标注记忆 μ 的更新。"
* "把下面这段 FSM 的迁移关系编码成 z3 的整数状态变量 + 嵌套 If，要求 s_{t+1} = δ(s_t, σ_t)，σ_t 不加约束。"
* "检查这条 LTL 的违反条件编码是否漏掉了窗口截断的情况。"

**核查清单（这部分比提示词更重要）**

1. 规则与代码是否一一对应 → `btfsv/sos.py` 的规则编号 vs `tree.py` 的分支；
2. 编码方向是否写反 → 用"必然违反"的性质做反向测试（`tests/test_verify.py::test_safety_property_is_detected_as_violated`）；
3. 反例是否真的违反 → 每条反例都回放到解释器上复核（`confirmed` 字段）；
4. 边界是否漏 → horizon 尾部窗口截断（本项目实际踩到过，见 `Encoder.query` 的注释）。

> 第 4 条建议在报告里写成一个小故事：AI 生成的编码最初在 horizon 末尾产生假反例，
> 后来通过"窗口必须完整落在 horizon 内"的约束修正。这是"AI 辅助 + 人工把关"的实证材料。

## 5. 答辩可能被问到的三个问题

1. **为什么是"有界"模型检测，不算完整证明？**
   因为 horizon=k 只覆盖长度 ≤k 的执行；unsat 只能说明"k 步内无反例"。
   完整证明需要 k-induction 或不变式合成，属于未来工作。
2. **为什么用 z3 而不是 NuSMV？**
   z3 是 SMT 求解器，便于把"动作时长/参数"当作整数编码，改动成本低；
   NuSMV 面向有限状态、原生支持 CTL/LTL，规模更大时更合适。二者可在同一 FSM 上交叉验证（见 README §8）。
3. **状态爆炸了怎么办？**
   三条：缩小 horizon 与原子命题数、换符号化表示（BDD/SMT）、按子树分解并行探索。
   实测数据在 `build/bench.md`。
